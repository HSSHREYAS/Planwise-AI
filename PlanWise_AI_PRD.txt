============================================================
1. PRODUCT OVERVIEW
============================================================

PlanWise AI is an agentic planning assistant that converts a user's natural-language goal into an executable, constraint-aware multi-step plan.

The system is designed to demonstrate the core concepts of agentic GenAI:

- Intent understanding
- Task decomposition
- Information retrieval
- Tool calling
- State management
- Constraint handling
- Verification
- Final response generation
- Replanning when requirements change
- Basic memory
- Agent evaluation

The system will support two primary use cases:

1. Trip planning
   Example:
   "I am travelling to Bengaluru for two days. Create a plan covering places to visit, food options and a reasonable schedule."

2. Personal/study planning
   Example:
   "Plan my study schedule for the next seven days."

A budget-constrained trip is another supported example:
"Create a one-day trip plan based on a ₹2,000 budget."

The project will use freely available MultiWOZ 2.2 data as the local knowledge source for relevant travel domains instead of paid travel APIs.

The implementation should remain intentionally focused on the requirements of this project. No unnecessary features, external services, or complex infrastructure should be introduced.

============================================================
2. PRODUCT GOAL
============================================================

Build a working AI agent that can:

1. Understand what the user wants.
2. Extract relevant constraints and preferences.
3. Break the goal into meaningful subtasks.
4. Select and invoke appropriate tools.
5. Maintain the user's current planning state.
6. Retrieve relevant information from the local dataset.
7. Generate a feasible schedule.
8. Check the generated plan against user constraints.
9. Reject or revise infeasible plans.
10. Re-plan when the user changes an important requirement.
11. Remember relevant preferences during the conversation.
12. Produce a coherent final plan through a simple Streamlit interface.

The primary success criterion is not conversational ability alone.

The system must demonstrate an actual agentic workflow in which the model reasons over a goal, uses tools, maintains state, validates constraints, and can revise an existing plan.

5.3 BUDGET-CONSTRAINED TRIP

User:
"Create a one-day trip plan based on a ₹2,000 budget."

The system should:

- understand the budget
- retrieve relevant options
- estimate the plan cost using available data
- generate a plan within the budget
- reject or revise a plan if the budget is exceeded

5.4 REPLANNING

Initial request:
"Plan a two-day trip with a ₹2,000 budget."

Follow-up:
"Reduce the budget to ₹1,500."

The system must:

- retain the existing planning state
- update the budget
- identify the changed constraint
- regenerate/revise the plan
- validate the revised plan
- present the updated plan

It must not behave as if the second request were an unrelated new conversation.

5.5 IMPOSSIBLE CONSTRAINTS

User:
"I have 2 days, ₹500, and want to visit 10 attractions."

The system should recognize that the constraints are unrealistic or infeasible and clearly explain the conflict rather than confidently producing an invalid schedule.

6. FUNCTIONAL REQUIREMENTS
============================================================

FR-01: USER INPUT

The system shall accept natural-language planning requests through the Streamlit UI.

FR-02: INTENT UNDERSTANDING

The system shall identify the user's primary planning intent.

Example:

Input:
"Find a reasonably priced hotel."

Output:

{
  "intent": "hotel_search",
  "budget": "reasonable"
}

The system should support relevant intents such as:

- hotel_search
- restaurant_search
- attraction_search
- transport_search
- trip_planning
- study_planning
- schedule_generation
- replanning

FR-03: INFORMATION EXTRACTION

The system shall extract relevant planning parameters, including where applicable:

- Location
- Dates
- Duration
- Budget
- Preferences
- Interests
- Food preferences
- Travel preferences
- Available time
- Existing selected options

FR-04: TASK DECOMPOSITION

The planning agent shall convert a high-level request into appropriate subtasks.

Example:

"Plan a two-day trip."

Possible subtasks:

1. Search accommodation.
2. Search attractions.
3. Search restaurants.
4. Search transport.
5. Build schedule.
6. Check budget.
7. Verify final plan.

The decomposition must depend on the user's request. The system should not invoke irrelevant tools unnecessarily.

FR-05: TOOL CALLING

The agent shall invoke tools using structured parameters.

Required tools:

- search_hotel()
- search_restaurant()
- search_attraction()
- search_transport()

Tools shall operate on local/static information derived from MultiWOZ 2.2.

FR-06: TOOL PARAMETER VALIDATION

Tool arguments shall be validated before execution.

Pydantic should be used for structured input validation where appropriate.

Invalid parameters must not silently execute.

FR-07: INFORMATION RETRIEVAL

The system shall retrieve relevant records from the prepared local domain knowledge.

FAISS shall be used as the recommended vector-search mechanism where semantic retrieval is appropriate.

FR-08: STATE MANAGEMENT

The system shall maintain the current planning state.

Minimum state:

- Location
- Dates/duration
- Budget
- Preferences
- Interests
- Chosen options
- Current plan
- Relevant user constraints

State must persist across turns within the active conversation.

FR-09: CONSTRAINT HANDLING

The system shall validate generated plans against known constraints.

Important constraints include:

- Budget
- Duration
- Time availability
- User preferences
- Number of days
- Schedule feasibility

The system shall identify constraint violations rather than blindly returning an invalid plan.

FR-10: SCHEDULE GENERATION

The system shall generate a coherent time-based plan.

Trip example:

Day 1 Morning
Day 1 Afternoon
Day 1 Evening
Day 2 Morning
Day 2 Afternoon
Day 2 Evening

The schedule should use retrieved options and user constraints.

FR-11: PLAN VERIFICATION

Before presenting the final plan, the system shall verify that the plan satisfies known constraints and does not contain obvious contradictions.

FR-12: REPLANNING

When a user changes a relevant requirement, the system shall update the current state and generate a revised plan.

Example:

Budget:
₹2,000 → ₹1,500

The agent should revise the existing plan instead of treating the request as a completely unrelated task.

FR-13: MEMORY

The system shall retain relevant preferences during the active planning conversation.

Examples:

- Vegetarian
- Preferred travel time
- Budget
- Interests

Memory should be used when generating subsequent plans.

FR-14: FINAL RESPONSE

The system shall present a clear final plan including:

- Selected activities/options
- Schedule
- Relevant cost information where available
- Important constraints
- Any limitations or infeasibility warnings

7. AGENT DESIGN
============================================================

The system should use a single small LLM sequentially for different agent roles.

Recommended LLM:

Qwen2.5-3B-Instruct

Recommended local runtime:

Ollama

The project does not require multiple expensive LLMs.

Logical agent responsibilities:

1. Intent Understanding
2. Task Planning
3. Tool Selection
4. State Update
5. Constraint/Verification Reasoning
6. Final Response Generation

These responsibilities may be implemented using a single model with structured prompts and a controlled Python workflow.

11. CONSTRAINT ENGINE
============================================================

Constraint validation should be implemented explicitly rather than relying only on free-form LLM output.

Minimum checks:

1. Budget constraint
2. Duration constraint
3. Time feasibility
4. Required preferences
5. Selected-option consistency

Example:

Input:

Budget = ₹2,000

Generated plan:

Estimated cost = ₹2,450

Result:

INVALID

The agent should receive the validation result and revise the plan.

For impossible constraints:

Input:

- 2 days
- ₹500
- 10 attractions

Expected behavior:

- identify infeasibility
- explain the main conflict
- avoid claiming that the plan satisfies all requirements
- request or suggest a relaxation only when appropriate

12. REPLANNING MODEL
============================================================

Replanning is a core requirement.

The system should treat the plan as stateful.

Example state:

{
  "location": "Bengaluru",
  "duration_days": 2,
  "budget": 2000,
  "preferences": ["vegetarian"],
  "interests": ["culture", "food"],
  "selected_options": [...],
  "current_plan": [...]
}

User changes:

"Reduce budget to ₹1500."

System:

1. Parse the new requirement.
2. Update budget.
3. Preserve unchanged state.
4. Identify affected decisions.
5. Recalculate/retrieve alternatives where necessary.
6. Generate revised schedule.
7. Validate constraints.
8. Return updated plan.

The state should not be unnecessarily discarded between related turns.

17. ERROR HANDLING
============================================================

The system should fail safely and clearly.

Examples:

Missing location:
"I need a destination to create the trip plan."

Missing duration:
"How many days should the trip cover?"

Impossible constraints:
"The requested activities cannot fit within the stated budget/time."

No matching dataset results:
"No suitable records were found in the available travel data."

Invalid tool parameters:
Reject the call and request correction/retry.

LLM malformed output:
Validate structured output and retry or return a controlled error.

The system should never silently fabricate retrieved dataset information.
