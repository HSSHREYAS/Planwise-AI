PLANWISE AI — COMPLETE SYSTEM ARCHITECTURE
Senior Software Engineering Design Specification

Project: PlanWise AI — Agentic Personal Task and Trip Planning Assistant
Deadline: 30-10-2026
Primary model: Qwen2.5-3B-Instruct
Runtime: Ollama
UI: Streamlit
Retrieval: FAISS
Validation/schema layer: Pydantic
Dataset: MultiWOZ 2.2
Orchestration: Plain Python state machine or LangGraph

======================================================================
1. ARCHITECTURE OBJECTIVE
======================================================================

PlanWise AI should implement one reliable end-to-end agentic planning
loop:

User Goal
    ↓
Input / Session Layer
    ↓
Goal Understanding
    ↓
Task Decomposition
    ↓
Plan Execution / Tool Selection
    ↓
Local Information Retrieval
    ↓
State Update
    ↓
Constraint Validation
    ↓
Schedule Generation
    ↓
Plan Verification
    ↓
Final Response

For a changed requirement:

Existing State
    ↓
New User Request
    ↓
Change Detection
    ↓
State Update
    ↓
Selective Replanning
    ↓
Tool Retrieval if required
    ↓
Constraint Validation
    ↓
Schedule Regeneration
    ↓
Verification
    ↓
Updated Response

The architecture must remain intentionally simple. The project does not
need multiple expensive LLMs, paid APIs, booking systems, maps, or a
complex distributed backend.

======================================================================
3. ARCHITECTURAL LAYERS
======================================================================

3.1 Presentation Layer

Technology:
- Streamlit

Responsibilities:
- Accept user input.
- Display conversation.
- Display generated plans.
- Display updated plans.
- Preserve the current UI session.
- Surface useful validation/error messages.

The UI must not contain planning logic.

Main entry point:
    app.py

The UI calls the application/controller layer and receives a structured
result.

--------------------------------------------------

3.2 Application / Controller Layer

Responsibilities:
- Receive a user request from Streamlit.
- Load/create the current agent state.
- Invoke the planner.
- Return the final result to the UI.
- Keep orchestration outside the UI.

Conceptually:

    handle_user_message(message, session_state)
        -> planner.run(message, session_state)
        -> updated_state + response

--------------------------------------------------

3.3 Agent Layer

The agent layer is the central intelligence/orchestration component.

Responsibilities:
- Understand intent.
- Extract parameters.
- Decompose goals.
- Decide which tools are required.
- Execute the plan.
- Update state.
- Trigger validation.
- Generate or regenerate a schedule.

Recommended implementation:
- A plain Python state machine for the fastest reliable implementation.
- LangGraph can replace the state machine if desired.

Do not create multiple independent LLM agents unless necessary.

A single Qwen2.5-3B-Instruct model can sequentially perform:
- intent extraction
- planning
- structured decision generation
- response generation

--------------------------------------------------

3.4 State Layer

The state layer stores all information needed to continue the current
conversation.

Minimum state:

    location
    dates / duration
    budget
    preferences
    chosen_options

Recommended internal state:

    conversation_history
    current_goal
    intent
    subtasks
    tool_results
    constraints
    selected_options
    current_plan
    validation_result

State should be represented using Pydantic models where practical.

Example conceptual state:

    PlanState
        goal
        intent
        location
        dates
        duration
        budget
        preferences
        interests
        subtasks
        tool_results
        chosen_options
        plan
        violations
        status

The state is the source of truth for the current planning session.

--------------------------------------------------

3.5 LLM Service Layer

The LLM service provides one controlled interface to Qwen2.5-3B-Instruct
running through Ollama.

Responsibilities:
- Send structured prompts.
- Request structured output.
- Parse model responses.
- Handle malformed output.
- Keep LLM-specific code out of the rest of the application.

Conceptual interface:

    llm.generate(prompt)
    llm.generate_structured(prompt, schema)

The planner should not directly depend on raw Ollama calls throughout
the codebase.

--------------------------------------------------

3.6 Tool Layer

The tool layer exposes domain-specific retrieval operations.

Required tools:

    search_hotel()
    search_restaurant()
    search_attraction()
    search_transport()

Responsibilities:
- Accept structured parameters.
- Query local/static data.
- Return structured results.
- Never fabricate results.

Tools should be deterministic.

Conceptual interface:

    search_hotel(
        location,
        budget=None,
        preferences=None
    )

    search_restaurant(
        location,
        preferences=None,
        budget=None
    )

    search_attraction(
        location,
        interests=None
    )

    search_transport(
        location,
        source=None,
        destination=None
    )

--------------------------------------------------

3.7 Retrieval Layer

The retrieval layer sits below the domain tools.

Pipeline:

    User/Agent Query
          ↓
    Query Normalization
          ↓
    Metadata / Domain Filtering
          ↓
    FAISS Similarity Search
          ↓
    Result Filtering
          ↓
    Ranking
          ↓
    Structured Tool Result

The retrieval layer should not generate answers.

Its job is to find relevant records.

--------------------------------------------------

3.8 Data Layer

The project uses MultiWOZ 2.2 as the primary dataset.

Relevant domains:

    Hotel
    Restaurant
    Attraction
    Train
    Taxi

Data should be transformed into application-friendly local records.

Recommended conceptual structure:

    raw MultiWOZ
         ↓
    preprocessing
         ↓
    normalized records
         ↓
    domain-specific data
         ↓
    searchable documents
         ↓
    FAISS index

No paid third-party travel APIs are required.

--------------------------------------------------

3.9 Constraint Layer

The constraint engine performs deterministic validation.

Responsibilities:
- Check budget.
- Check duration.
- Check preferences.
- Check required activities.
- Identify conflicts.
- Report violations.

The constraint engine should not depend on the LLM for arithmetic or
basic rule checking.

Example:

    total_cost <= budget

If false:

    violation = "Budget exceeded"

The planner then decides whether to replan.

--------------------------------------------------

3.10 Verification Layer

The verifier checks the final plan before it is shown to the user.

Checks include:
- Plan contains requested components.
- Options came from available retrieved data.
- Budget is respected.
- Duration is respected.
- Preferences are respected where applicable.
- Schedule is internally coherent.
- No known constraint violation remains.

If verification fails:

    plan
      ↓
    verifier
      ↓
    failure
      ↓
    planner / replanner
      ↓
    new plan

--------------------------------------------------

3.11 Response Layer

The response generator converts the verified structured plan into a
clear user-facing response.

The response should contain:
- Schedule.
- Relevant options.
- Budget information where applicable.
- Important constraint notes.
- Replanning explanation where relevant.

The response generator should not introduce facts absent from the
structured plan/retrieved data.

======================================================================
4. CORE EXECUTION FLOW
======================================================================

The normal execution flow should be:

STEP 1 — RECEIVE

User sends a natural-language request.

Example:

    "Plan a two-day trip with a ₹2,000 budget."

STEP 2 — UNDERSTAND

Extract:
- intent
- location
- duration
- budget
- preferences
- interests
- requested activities

STEP 3 — VALIDATE INPUT

Check whether enough information exists.

If essential information is missing, ask the user instead of guessing.

STEP 4 — DECOMPOSE

Convert the goal into subtasks.

Example:

    search_attractions
    search_restaurants
    search_transport
    build_schedule
    check_budget

STEP 5 — SELECT TOOLS

Map subtasks to tools.

Example:

    search_attractions -> search_attraction()
    search_restaurants -> search_restaurant()
    search_transport -> search_transport()

STEP 6 — EXECUTE TOOLS

Call tools with structured parameters.

STEP 7 — UPDATE STATE

Store:
- retrieved options
- chosen options
- constraints
- relevant user preferences

STEP 8 — GENERATE CANDIDATE PLAN

Create a schedule using the retrieved options.

STEP 9 — CONSTRAINT CHECK

Run deterministic checks.

STEP 10 — VERIFY

Check the plan for consistency and unsupported information.

STEP 11 — REPLAN IF REQUIRED

If constraints fail, revise the plan.

STEP 12 — RESPOND

Return the verified final plan to the user.

======================================================================
5. REPLANNING ARCHITECTURE
======================================================================

Replanning is a first-class operation.

Example:

Initial:

    "Plan two days in Bengaluru with ₹2,000."

State:

    location = Bengaluru
    duration = 2 days
    budget = 2000

User:

    "Reduce the budget to ₹1,500."

The system should NOT rebuild the conversation from scratch.

Flow:

    New message
         ↓
    Change extraction
         ↓
    Existing state
         ↓
    Update budget
         ↓
    Determine affected tasks
         ↓
    Reuse unaffected information
         ↓
    Re-run affected retrieval/planning
         ↓
    Validate
         ↓
    Verify
         ↓
    Return revised plan

This makes the system genuinely stateful.

======================================================================
6. SELECTIVE REPLANNING
======================================================================

The architecture should avoid unnecessary work.

Examples:

If budget changes:
    - Recheck cost-sensitive options.
    - Regenerate schedule.
    - Revalidate budget.

If vegetarian preference changes:
    - Recheck restaurant selection.
    - Preserve unrelated attractions.
    - Regenerate affected portions.

If duration changes:
    - Recalculate schedule.
    - Re-evaluate attraction count.
    - Revalidate constraints.

If location changes:
    - Existing location-specific retrieval results become invalid.
    - Re-run relevant searches.

The implementation can initially use full replanning for simplicity.
Selective replanning is the preferred architectural behavior when easy
to implement.

8. STRUCTURED DATA CONTRACTS
======================================================================

Pydantic should define important boundaries.

Example conceptual models:

UserRequest:
    message: str

IntentResult:
    intent: str
    location: optional str
    duration: optional int
    budget: optional float
    preferences: list
    interests: list

Task:
    task_id: str
    task_type: str
    parameters: dict
    status: str

ToolResult:
    tool_name: str
    success: bool
    results: list
    error: optional str

ConstraintResult:
    valid: bool
    violations: list
    warnings: list

Plan:
    location: str
    days: list
    estimated_cost: optional float
    assumptions: list

AgentResponse:
    plan: optional Plan
    message: str
    state: PlanState

The exact implementation can be simplified, but the interfaces should
remain structured.

======================================================================
9. TOOL REGISTRY
======================================================================

The planner should use a central tool registry.

Conceptually:

    TOOL_REGISTRY = {
        "hotel_search": search_hotel,
        "restaurant_search": search_restaurant,
        "attraction_search": search_attraction,
        "transport_search": search_transport
    }

This provides:
- Clear tool discovery.
- Easy extension within the existing project scope.
- Centralized tool invocation.
- Better testing.

The LLM should output a tool name and structured arguments. The
application validates the requested tool before execution.

======================================================================
10. LLM OUTPUT CONTRACT
======================================================================

Prefer structured output instead of unrestricted natural language for
intermediate agent decisions.

Example:

    {
      "intent": "trip_planning",
      "location": "Bengaluru",
      "duration": 2,
      "budget": 2000,
      "preferences": ["vegetarian"]
    }

Planner output:

    {
      "tasks": [
        {
          "type": "search_attractions",
          "parameters": {
            "location": "Bengaluru"
          }
        },
        {
          "type": "search_restaurants",
          "parameters": {
            "location": "Bengaluru",
            "preference": "vegetarian"
          }
        }
      ]
    }

The Python layer validates these outputs before execution.

======================================================================
11. PROMPT ARCHITECTURE
======================================================================

Keep prompts separated from Python implementation.

Recommended prompt categories:

    intent_prompt
    decomposition_prompt
    tool_selection_prompt
    schedule_prompt
    replanning_prompt
    response_prompt

Prompts should clearly tell the model:
- What role it is performing.
- What state it receives.
- What information it may use.
- What output schema is expected.
- That it must not invent unavailable data.

Do not create unnecessarily complicated prompt chains.

======================================================================
12. CONSTRAINT ENGINE DESIGN
======================================================================

Constraints should be represented explicitly.

Example:

    constraints = {
        "budget": 2000,
        "duration_days": 2,
        "preferences": ["vegetarian"]
    }

Validation functions can include:

    check_budget(plan, budget)
    check_duration(plan, duration)
    check_preferences(plan, preferences)
    check_required_components(plan, requirements)

Then:

    validate_plan(plan, constraints)

returns:

    valid
    violations
    warnings

The constraint engine should be deterministic and unit-testable.

======================================================================
13. HALLUCINATION-CONTROL ARCHITECTURE
======================================================================

The most important boundary is:

    Retrieved Data → Planning → Validation → Response

rather than:

    User → LLM → invented facts

Rules:
1. Domain facts should originate from local data/tool results.
2. Tool results should be structured.
3. The planner should only select from available results.
4. Budget calculations should be programmatic.
5. Constraint checks should be programmatic.
6. The verifier should reject unsupported selections.
7. Missing information should trigger clarification rather than
   fabrication.

14. ERROR-HANDLING FLOW
======================================================================

Case A — Missing information

    User request
        ↓
    Required parameter missing
        ↓
    Ask clarification
        ↓
    Wait for user

Case B — No retrieval results

    Tool
      ↓
    No result
      ↓
    Planner informed
      ↓
    Try another valid option / explain limitation

Case C — Tool failure

    Tool
      ↓
    Error
      ↓
    Structured failure
      ↓
    Controlled response

Case D — Constraint violation

    Candidate plan
        ↓
    Validator
        ↓
    Violation
        ↓
    Replan

Case E — Impossible constraints

    Validator
        ↓
    Cannot satisfy constraints
        ↓
    Explain conflict
        ↓
    Ask user to relax a constraint if needed

======================================================================
22. PERFORMANCE ARCHITECTURE
======================================================================

The system is designed for local execution.

Primary latency sources:
- Qwen2.5-3B inference.
- Retrieval.
- Multiple sequential planning steps.

Keep latency reasonable by:
- Reusing state.
- Avoiding unnecessary LLM calls.
- Avoiding duplicate retrieval.
- Using deterministic Python logic for validation.
- Using one small model.
- Keeping prompts concise.
- Limiting retrieval results to relevant top-k records.

Do not optimize prematurely.

Measure:
- Total response latency.
- LLM latency.
- Retrieval latency.
- Number of LLM calls.
- Number of tool calls.

======================================================================
23. SECURITY / SAFETY BOUNDARIES
======================================================================

For this project, security requirements should remain lightweight.

Important boundaries:
- Validate tool names.
- Validate structured parameters.
- Never execute arbitrary code generated by the LLM.
- Never allow the model to directly access the filesystem through
  arbitrary commands.
- Keep tool functions explicitly defined.
- Treat LLM output as untrusted input.
- Validate all structured outputs before execution.

The LLM should request an operation; Python decides whether and how that
operation executes.

27. DEPENDENCY DIRECTION
======================================================================

Keep dependencies flowing in one direction:

    UI
     ↓
    Application
     ↓
    Agent
     ↓
    Services / Tools / State
     ↓
    Retrieval / Data

Validation should remain independently callable by the agent.

Avoid:
- UI importing retrieval internals.
- Tools directly modifying UI state.
- LLM client containing business logic.
- Constraint logic inside prompts.
- Random modules making uncontrolled model calls.

28. STATE TRANSITION MODEL
======================================================================

The agent can be modeled with these states:

    RECEIVED
       ↓
    UNDERSTANDING
       ↓
    DECOMPOSING
       ↓
    EXECUTING
       ↓
    PLANNING
       ↓
    VALIDATING
       ↓
    VERIFYING
       ↓
    COMPLETED

Failure:

    any state
       ↓
    ERROR / RECOVERY

Replanning:

    VALIDATING
       ↓
    CONSTRAINT_VIOLATION
       ↓
    REPLANNING
       ↓
    EXECUTING / PLANNING
       ↓
    VALIDATING

Clarification:

    UNDERSTANDING
       ↓
    MISSING_INFORMATION
       ↓
    WAITING_FOR_USER
       ↓
    UNDERSTANDING

======================================================================
29. CORE ALGORITHM
======================================================================

High-level pseudocode:

    handle_message(message, state):

        request = understand(message, state)

        state = update_state(state, request)

        if missing_required_information(state):
            return clarification_response(state)

        tasks = decompose_goal(state)

        for task in tasks:

            if task.requires_tool:
                result = execute_tool(task)
                state = update_with_result(state, result)

        candidate_plan = generate_plan(state)

        validation = validate(candidate_plan, state)

        if not validation.valid:

            state.violations = validation.violations

            candidate_plan = replan(state)

            validation = validate(candidate_plan, state)

        if not validation.valid:
            return explain_constraint_failure(state)

        verification = verify(candidate_plan, state)

        if not verification.valid:
            return recovery_or_replan(state)

        state.current_plan = candidate_plan

        return generate_response(candidate_plan, state)

30. ARCHITECTURAL DECISIONS
======================================================================

DECISION 1 — One small LLM

Use Qwen2.5-3B-Instruct for all language/planning roles.

Reason:
- Lower complexity.
- Lower resource requirements.
- Matches the project specification.
- Easier to run locally.

DECISION 2 — Deterministic tools

Use Python functions for tool execution.

Reason:
- Reliable.
- Testable.
- Prevents uncontrolled LLM actions.

DECISION 3 — Deterministic constraints

Budget and basic constraint checks should be Python logic.

Reason:
- LLM arithmetic and rule enforcement can be unreliable.

DECISION 4 — Explicit state

Maintain structured state.

Reason:
- Required for replanning and memory.

DECISION 5 — Local/static data

Use MultiWOZ-derived local data.

Reason:
- No paid APIs.
- Reproducible.
- Matches project requirements.

DECISION 6 — Simple orchestration

Use a Python state machine or LangGraph.

Reason:
- Both represent the required sequential agent workflow.
- Plain Python is the fastest implementation path.

DECISION 7 — Streamlit

Use Streamlit for the UI.

Reason:
- Minimal frontend complexity.
- Sufficient for the project's requirements.

34. FINAL ARCHITECTURAL PRINCIPLE
======================================================================

PlanWise should be engineered around one central separation:

    LLM = Understand + Reason + Plan + Communicate

    PYTHON = State + Tools + Rules + Validation

    DATA = Grounding

    FAISS = Retrieval

    STREAMLIT = Interaction

This separation is the most important architectural decision in the
project.

The LLM should not control the entire application.

Instead:

    USER
      ↓
    LLM — understand
      ↓
    PYTHON — decide/validate execution
      ↓
    TOOLS — retrieve
      ↓
    STATE — remember
      ↓
    PYTHON — enforce constraints
      ↓
    LLM — generate plan
      ↓
    PYTHON — verify
      ↓
    USER
