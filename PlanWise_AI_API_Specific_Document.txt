PLANWISE AI — API-SPECIFIC DOCUMENT
Frontend ↔ Backend API Contracts

Version: 1.0
Project: PlanWise AI — Agentic Personal Task and Trip Planning Assistant

======================================================================
1. PURPOSE
======================================================================

This document defines the complete API contract between the PlanWise
frontend and backend.

IMPORTANT ARCHITECTURAL NOTE

The selected project stack uses Streamlit as the frontend and Python as
the backend/application layer. Therefore, the core implementation does
NOT require a separate public REST API server.

The APIs defined in this document are the logical backend service
contracts that the frontend uses.

Implementation options:

PRIMARY:
    Streamlit
        ↓
    Python Application Controller
        ↓
    Agent / Services / Tools

OPTIONAL:
    Streamlit
        ↓
    REST API layer
        ↓
    Python Backend

If a REST API is required later, these contracts can be exposed through
FastAPI without changing the underlying business logic.

No paid external travel APIs are required.

3. API DESIGN PRINCIPLES
======================================================================

1. Frontend never directly calls Ollama.
2. Frontend never directly calls FAISS.
3. Frontend never directly accesses raw dataset files.
4. Frontend never executes tools directly.
5. Backend owns all business logic.
6. LLM output is treated as untrusted input.
7. Tool parameters are validated before execution.
8. Constraints are checked programmatically.
9. Backend returns structured responses.
10. Frontend is responsible only for presentation and interaction.
11. No paid third-party travel API is required.
12. API contracts should remain stable even if internal implementation
    changes.

6. HEALTH API
======================================================================

Endpoint:

    GET /api/v1/health

Purpose:
    Check whether the backend is available.

Frontend usage:
    Application startup / debugging.

Response:

    {
      "status": "ok",
      "service": "planwise-api"
    }

Possible status:

    200 OK

No user/session information should be returned.

======================================================================
7. CREATE SESSION API
======================================================================

Endpoint:

    POST /api/v1/sessions

Purpose:
    Create a new planning session.

Frontend:
    Streamlit application.

Request:

    {
      "user_id": null
    }

For the current project, user authentication is not required.

Response:

    {
      "session_id": "generated-session-id",
      "status": "active"
    }

The session_id is then used by all subsequent requests.

======================================================================
8. GET SESSION API
======================================================================

Endpoint:

    GET /api/v1/sessions/{session_id}

Purpose:
    Retrieve current planning state.

Response:

    {
      "session_id": "...",
      "status": "active",
      "state": {
        "location": "Bengaluru",
        "duration_days": 2,
        "budget": 2000,
        "preferences": ["vegetarian"],
        "interests": [],
        "chosen_options": [],
        "current_plan": null
      }
    }

Frontend usage:
    Restore/display current planning context.

======================================================================
9. SEND MESSAGE API
======================================================================

Endpoint:

    POST /api/v1/sessions/{session_id}/messages

Purpose:
    Main frontend-to-agent endpoint.

This is the most important API in the system.

Request:

    {
      "message": "Plan a two-day trip with a budget of ₹2,000."
    }

Backend flow:

    Message
       ↓
    Intent Understanding
       ↓
    State Update
       ↓
    Task Decomposition
       ↓
    Tool Selection
       ↓
    Tool Execution
       ↓
    Candidate Plan
       ↓
    Constraint Validation
       ↓
    Verification
       ↓
    Replanning if required
       ↓
    Final Response

Response:

    {
      "session_id": "...",
      "status": "completed",
      "intent": {
        "name": "trip_planning",
        "location": "Bengaluru",
        "duration_days": 2,
        "budget": 2000,
        "preferences": []
      },
      "plan": {
        "days": []
      },
      "validation": {
        "valid": true,
        "violations": [],
        "warnings": []
      },
      "message": "..."
    }

======================================================================
10. MESSAGE RESPONSE STATES
======================================================================

The API may return:

completed

    Plan successfully generated.

clarification_required

    Required information is missing.

replanning

    Existing plan is being modified.

constraint_failure

    Requested constraints cannot currently be satisfied.

tool_failure

    Required local tool/data operation failed.

error

    Unexpected application error.

Example clarification response:

    {
      "status": "clarification_required",
      "message": "What location would you like to plan for?"
    }

12. REPLAN API
======================================================================

Endpoint:

    POST /api/v1/sessions/{session_id}/replan

Purpose:
    Explicitly request replanning after a requirement changes.

Request example:

    {
      "changes": {
        "budget": 1500
      }
    }

Other examples:

    {
      "changes": {
        "preferences": ["vegetarian"]
      }
    }

    {
      "changes": {
        "duration_days": 1
      }
    }

Backend flow:

    Existing State
         ↓
    Apply Changes
         ↓
    Identify affected requirements
         ↓
    Retrieve new information if required
         ↓
    Generate revised plan
         ↓
    Validate
         ↓
    Verify
         ↓
    Return updated plan

Response:

    {
      "session_id": "...",
      "status": "completed",
      "changes_applied": {
        "budget": 1500
      },
      "plan": {},
      "validation": {
        "valid": true,
        "violations": [],
        "warnings": []
      },
      "message": "Plan updated for the new budget."
    }

17. PLAN VALIDATION API
======================================================================

Endpoint:

    POST /api/v1/validation/plan

Purpose:
    Validate a candidate plan independently.

Request:

    {
      "plan": {},
      "constraints": {
        "budget": 2000,
        "duration_days": 2,
        "preferences": ["vegetarian"]
      }
    }

Response:

    {
      "valid": false,
      "violations": [
        "Estimated cost exceeds budget."
      ],
      "warnings": []
    }

This API should call deterministic Python validation logic.

The LLM should NOT decide whether the budget arithmetic is valid.

======================================================================
18. INTERNAL LLM SERVICE
======================================================================

The LLM should NOT be exposed directly to the frontend.

Frontend:

    Streamlit
       ↓
    Message API
       ↓
    Planner
       ↓
    LLM Service
       ↓
    Ollama
       ↓
    Qwen2.5-3B-Instruct

Internal interface:

    generate(prompt)

and preferably:

    generate_structured(prompt, schema)

Responsibilities:
- Intent extraction
- Task decomposition
- Tool selection
- Plan generation
- Replanning
- Final response generation

The frontend must never send arbitrary prompts directly to Ollama.

======================================================================
19. INTERNAL RETRIEVAL SERVICE
======================================================================

The frontend should NOT directly access FAISS.

Flow:

    Frontend
       ↓
    Message API
       ↓
    Planner
       ↓
    Domain Tool
       ↓
    Retrieval Service
       ↓
    FAISS
       ↓
    Local MultiWOZ Data

Internal operations:

    search(domain, query, filters, top_k)

Example:

    search(
        domain="restaurant",
        query="vegetarian restaurant in Bengaluru",
        filters={...},
        top_k=5
    )

======================================================================
22. API REQUEST VALIDATION
======================================================================

All incoming API payloads should be validated using Pydantic.

Examples:

    MessageRequest
    SessionCreateRequest
    ReplanRequest
    HotelSearchRequest
    RestaurantSearchRequest
    AttractionSearchRequest
    TransportSearchRequest
    PlanValidationRequest

Invalid requests should return a structured error.

Example:

    {
      "error": {
        "code": "INVALID_REQUEST",
        "message": "Budget must be a positive number."
      }
    }

======================================================================
23. ERROR RESPONSE FORMAT
======================================================================

Use one consistent format.

Example:

    {
      "error": {
        "code": "TOOL_FAILURE",
        "message": "Unable to retrieve restaurant data."
      }
    }

Recommended error codes:

    INVALID_REQUEST
    SESSION_NOT_FOUND
    MISSING_INFORMATION
    TOOL_FAILURE
    NO_RESULTS
    CONSTRAINT_VIOLATION
    PLAN_VERIFICATION_FAILED
    LLM_FAILURE
    INTERNAL_ERROR

The frontend should display a human-readable message rather than raw
Python exceptions.

27. API SECURITY BOUNDARY
======================================================================

The LLM is never trusted to directly execute an arbitrary API operation.

Correct:

    LLM
      ↓
    Structured tool request
      ↓
    Pydantic validation
      ↓
    Tool registry
      ↓
    Approved Python function
      ↓
    Local data

Incorrect:

    LLM
      ↓
    Arbitrary Python/code/API execution

All tool calls must be explicitly registered.

======================================================================
28. API RESPONSIBILITY BOUNDARIES
======================================================================

FRONTEND:
- Collect input.
- Display state/results.
- Send API requests.
- Render errors.

APPLICATION API:
- Authenticate/validate request if applicable.
- Load session.
- Call planner.
- Return structured result.

PLANNER:
- Understand.
- Decompose.
- Select tools.
- Plan.
- Replan.

LLM SERVICE:
- Language and reasoning operations.

TOOLS:
- Controlled domain retrieval.

RETRIEVAL:
- Search local data.

STATE:
- Maintain planning context.

CONSTRAINT ENGINE:
- Deterministic validation.

VERIFIER:
- Final correctness checks.

33. FINAL ENGINEERING RULE
======================================================================

The frontend should know only about:

    Session
    Message
    Plan
    Replan
    Health

The frontend should NOT know about:

    Qwen
    Ollama
    FAISS
    MultiWOZ
    Prompt engineering
    Tool implementation
    Constraint implementation
    Agent state transitions

This keeps the frontend thin and the backend modular.

The backend can therefore evolve internally without requiring changes
to the Streamlit UI.
